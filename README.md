# JevTest

Evaluating [Jev](https://typesafe.ai) (TypeSafe's typed decision model) as a
replacement for the LLM-based query classifier in
[ragsha-agent](https://github.com/FufongLabs/ragsha-agent)'s router.

## Layout

```
golden_queries.json     135 labeled queries, copied from ragsha-agent/tests/data
scripts/
  eval_common.py         shared harness: runs a classify_fn over the golden set,
                          builds accuracy/cost/latency stats, writes outputs/
  jev/
    classifier.py         classify_via_jev() — calls Jev via OpenRouter's alpha
                           decisions endpoint
    evaluate.py            full golden-set run
    demo.py                 minimal example, all three question types
  llm/
    classifier.py         classify_via_llm() — the LLM router step (same
                           prompt/model as ragsha-agent), via OpenRouter
    evaluate.py             full golden-set run
  heuristic/
    evaluate.py            runs ragsha-agent's real _classify_heuristic
                           (imported from the submodule, not reimplemented)
  judge/
    evaluate.py            judge (LLM or Jev) on forced conflicts —
                           --backend llm|jev, --conflicts real|synthetic
  compare/
    compare.py              outputs/comparison.json (jev vs llm)
    table.py                 outputs/comparison_table.md
    judge_table.py            outputs/judge_comparison_table_{real,synthetic}.md
outputs/                 generated by the scripts above — not hand-written
stack/                   docker-compose overlay + a stub CE backend, for
                         running ragsha-deploy's full stack with Jev as the
                         router (see "Full-stack test" below)
ragsha-agent/            submodule; the router this whole project targets.
                         The Jev integration lives on its oat/jev-router
                         branch (router/classifier.py, config.py, app.py)
ragsha-deploy/           submodule; docker-compose for the full stack
                         (frontend + gateway + GK)
```

## Setup

```bash
pip install -r requirements.txt
cp .env.example .env    # fill in OPENROUTER_API_KEY
git submodule update --init --recursive
```

Two separate `.env` files are involved, because `judge/evaluate.py` and
`llm/classifier.py` reuse code and settings straight from the `ragsha-agent`
submodule instead of reimplementing them:

| File | Used by | Needs |
|---|---|---|
| `JevTest/.env` | `jev/*`, `llm/*` | `OPENROUTER_API_KEY`, `JEV_MODEL` (optional, defaults to `~typesafe/jev-latest`) |
| `ragsha-agent/.env` | `judge/evaluate.py` | `LLM_API_KEY`, `JUDGE_MODEL` (defaults to `google/gemini-2.5-pro`), `JEV_MODEL`/`JEV_API_URL` (optional) |

`heuristic/evaluate.py` needs neither — it's a pure function, no network call.

All commands below run from the `JevTest/` root, as modules (`python -m
scripts....`), not as bare scripts — they use package-relative imports.

## Quick look at Jev

```bash
python -m scripts.jev.demo   # one call, all three question types (Choice/Score/Noul)
```

## Running the evaluators

```bash
python -m scripts.heuristic.evaluate           # free, instant
python -m scripts.jev.evaluate                  # ~$0.003 total (135 calls)
python -m scripts.llm.evaluate                  # ~$0.024 total (135 calls)
```

Each writes `outputs/<name>_outputs.json` (per-query results, full raw
response) and `outputs/<name>_stats.json` (accuracy, confusion matrix,
latency, cost). Add `--summary` to skip the misclassified-queries printout.

### Judge

The judge only ever runs in production when the heuristic and router
disagree, so there's no "judge on every query" baseline — `judge/evaluate.py`
builds a conflict set first, then sends it to either judge backend.

```bash
# real: genuine heuristic-vs-LLM disagreements (reuses outputs/llm_outputs.json,
# no new LLM router calls) — whatever that run's true disagreement count is
python -m scripts.judge.evaluate --backend llm --conflicts real
python -m scripts.judge.evaluate --backend jev --conflicts real

# synthetic: first N golden queries, heuristic result paired with a forced
# wrong label — biased (see the docstring), kept for reference only
python -m scripts.judge.evaluate --backend llm --conflicts synthetic --n 12
python -m scripts.judge.evaluate --backend jev --conflicts synthetic --n 12
```

`--backend llm` costs real money per call (`JUDGE_MODEL`, e.g.
`google/gemini-2.5-pro` — several cents for a handful of calls). `--backend
jev` costs fractions of a cent.

### Compare

Run after the relevant evaluators above have produced their `outputs/*_stats.json`:

```bash
python -m scripts.compare.table          # outputs/comparison_table.md (jev vs llm)
python -m scripts.compare.compare        # outputs/comparison.json (same, structured)
python -m scripts.compare.judge_table --conflicts real   # outputs/judge_comparison_table_real.md
```

## Full-stack test

`stack/docker-compose.jev.yml` overlays `ragsha-deploy`'s compose file: it
builds the gateway from the local `ragsha-agent` checkout (so it picks up
the `oat/jev-router` branch) instead of the deploy repo's pinned version, and
adds a stub CE backend (`stack/ce-stub/`, echoes the query — not real RAG) so
CE-routed queries and conversation history both work without a real CE
service running.

```bash
cd ragsha-deploy
cp .env.example .env    # add LLM_API_KEY, and ROUTER_BACKEND=jev
cd ..
docker compose -f ragsha-deploy/docker-compose.yml -f stack/docker-compose.jev.yml up -d --build
curl http://localhost:8000/health
```

The gateway logs its startup line as `router=jev:<model>` when this is
working. GK has no data loaded in this setup, so `gk`-routed queries route
correctly but return an empty answer.
